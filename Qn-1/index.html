01
The big picture

Internet Overview

The Internet is a massive network of interconnected networks that spans the globe. No single organisation owns it; instead, thousands of independent networks — run by universities, governments, internet service providers (ISPs), and companies — agree to speak the same language (the TCP/IP protocol suite) so that any two connected devices, anywhere on Earth, can exchange data.

It is worth separating two terms that are often used interchangeably:

The Internet

The physical and logical infrastructure — cables, routers, satellites, and the addressing rules that let data packets travel between machines.

The World Wide Web

A service that runs on top of the Internet: a collection of linked documents (web pages) accessed using HTTP/HTTPS and displayed by a browser. Email, video calls, and file transfer also run on the Internet but are not "the Web".

  • Global reach — any connected device can, in principle, communicate with any other.
  • Decentralised — no single point of ownership or control; resilient by design.
  • Protocol-driven — TCP/IP defines how data is broken into packets, addressed, and reassembled.
  • Foundation for services — the Web, email, VoIP, and file sharing are all applications built on it.
02
Plumbing underneath

Fundamental Computer Network Concepts

A computer network is a set of devices connected together so they can share data and resources. A few core ideas make this possible:

Network scale: LAN / MAN / WAN

LAN covers a single building (a college lab). MAN spans a city. WAN spans countries — the Internet is the largest WAN of all.

IP Address

A unique numeric label (e.g. 192.168.1.10 or an IPv6 equivalent) assigned to every device, so data knows where to go.

Protocols

Agreed rules for communication — TCP/IP for delivery, HTTP/HTTPS for web pages, FTP for files.

Packet Switching

Data is split into small packets, each routed independently, and reassembled at the destination — far more efficient and fault-tolerant than a single dedicated line.

03
The address on the envelope

URL and its Structure

A URL (Uniform Resource Locator) is the address used to locate a specific resource on the web. Every part of it has a job:

  • Scheme — the protocol, typically http or the encrypted https.
  • Host — the domain name (or IP) identifying the server.
  • Port — usually hidden because 80 (HTTP) / 443 (HTTPS) are defaults.
  • Path — the specific file or route on that server.
  • Query string — optional parameters sent to the server, starting with ?.
  • Fragment — jumps the browser to a section within the loaded page; never sent to the server.
04
Names, not numbers

Domain Name

Computers route traffic using IP addresses, but humans remember names, not numbers. A domain name (e.g. kpriet.ac.in) is a human-readable label mapped to an IP address by the Domain Name System (DNS) — effectively the Internet's phone book.

  • Top-Level Domain (TLD) — .com, .org, .in, .edu.
  • Second-Level Domain — the organisation's chosen name, e.g. kpriet.
  • Subdomain — an optional prefix like www or admissions.
  • Registrar — the accredited body a domain is purchased and renewed through.
05
The two ends of every request

Web Browsers and Web Servers

Web Browser

Client software (Chrome, Firefox, Edge, Safari) that sends requests, then parses and renders HTML, CSS, and JavaScript into the visual page a user sees and interacts with.

Web Server

Software (Apache, Nginx, IIS) running on a remote machine that listens for requests, locates or generates the requested resource, and sends it back as a response.

Both sides speak HTTP/HTTPS: a shared request–response protocol that defines exactly how a browser asks for something and how a server must answer.

06
Putting it all together

Working Principle of a Website

When a visitor types the institution's web address, a precise sequence unfolds in a fraction of a second:

  • Request — the browser sends an HTTP request for a URL.
  • Resolution — DNS converts the domain to an IP address; a connection is established.
  • Processing — the server locates a static file or runs a program to build the page.
  • Response — HTML, CSS, JavaScript, and any data are sent back.
  • Rendering — the browser parses and paints the final, interactive page.
07
Where the code actually runs

Client-side vs Server-side Scripting

Not all website logic runs in the same place. Some code executes on the visitor's own device; other code executes on the institution's server before anything is even sent out.

Aspect Client-side Server-side
Runs on The visitor's browser The web server
Typical languages JavaScript (+ HTML/CSS) PHP, Node.js, Python, Java, ASP.NET
Sees source code? Yes — visible via "View Source" No — hidden from the visitor
Good for Form validation, animations, instant UI feedback Database access, authentication, business logic
Dependent on User's device & browser capability Server's own resources — consistent for everyone
Security-sensitive data Should never be placed here Belongs here — kept off the client entirely

A real website almost always uses both: client-side scripting for a responsive interface, and server-side scripting for anything that must be trusted, secured, or shared across all users — such as processing the institution's own admission form.

Conclusion

The Web is a document-sharing service layered on top of the Internet's global network of networks. A URL addresses a resource, DNS turns its domain name into a routable IP address, and a browser and server exchange that resource over HTTP through a request–response cycle. Understanding where client-side code ends and server-side code begins is the first real design decision for any new website — including the one this institution is about to build.
